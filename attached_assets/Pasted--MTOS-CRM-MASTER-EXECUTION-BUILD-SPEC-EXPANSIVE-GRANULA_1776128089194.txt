6. FRAUD DETECTION MUST ROUTE — NEVER SILENTLY IGNORE

3. FORM ENGINE (DETAILED IMPLEMENTATION)

3.1 FORM FACTORY PIPELINE

INPUT:
- tort_id
- tort_schema
- buyer criteria

PROCESS:
1. Load tort template
2. Merge global schema
3. Inject tort-specific fields
4. Inject compliance fields
5. Attach validation rules
6. Generate HTML + JS bundle
7. Store versioned form
8. Generate embed script


---

3.2 EMBED OUTPUT

<script src="https://crm.com/embed.js?tort_id=XXX"></script>
<div id="mtos-form"></div>


---

3.3 CLIENT-SIDE VALIDATION (NON-TRUSTED)

EMAIL VALIDATION

RULES:
- RFC 5322 format validation
- block typo domains:
  gnail, gmial, hotmial, yaho, outlookk
- block invalid TLD:
  .vom, .con, .cmo

FAIL:
→ block submission
→ show inline correction message


---

ADDRESS VALIDATION

RULES:
- all required fields present
- ZIP = 5-digit or ZIP+4
- valid US state code

OPTIONAL:
- USPS API verification hook

FAIL:
→ block submission

6. TORT RULE ENGINE (DETERMINISTIC LOGIC)

For each tort:

DEFINE:
- required exposure condition
- valid diagnosis list
- required fields override
- rejection conditions


---

EXECUTION RULE

IF exposure missing → REJECT
IF diagnosis mismatch → REJECT
IF partial evidence → REVIEW


---

7. NPI + TAXONOMY ENGINE (MEDICAL VALIDATION CORE)

PROCESS FLOW

1. Extract physician info
2. Query NPPES API
3. Retrieve:
   - NPI number
   - taxonomy code
   - specialty classification
4. Match taxonomy vs diagnosis


---

FRAUD RULE

IF diagnosis = cancer
AND physician taxonomy NOT IN:
  oncology
  hematology
  internal medicine (oncology-related)

→ FLAG FRAUD
→ ROUTE TO REVIEW


---

EXAMPLE

Pediatrician + Adult Cancer Claim
→ INVALID
→ TO_BE_REVIEWED


---

8. FRAUD DETECTION ENGINE

TRIGGERS

- taxonomy mismatch
- missing NPI
- inconsistent exposure logic
- invalid tort mapping
- impossible medical timeline


---

OUTPUT STATES

ACCEPTED
REJECTED
TO_BE_REVIEWED
