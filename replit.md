# Overview

This project is a full-stack Mass Tort Operating System (MTOS), a distributed case processing CRM designed for mass tort law firms. It aims to streamline the entire legal process from lead intake and document management to case analysis, compliance, and distributed processing. The system incorporates AI for medical document extraction, advanced validation engines, and robust conflict resolution. It features a sophisticated form engine for compliant lead generation across 24 tort campaigns and a comprehensive analytics suite. The core business vision is to provide a scalable, efficient, and compliant solution to manage complex mass tort litigation, significantly improving operational efficiency and compliance for law firms.

# System Architecture

The project is structured as a pnpm monorepo using TypeScript, targeting Node.js 24. The backend is an Express 5 API, integrated with a PostgreSQL database using Drizzle ORM. API codegen is handled by Orval from an OpenAPI specification. The UI/UX is built with React and Vite.

**Core Architectural Patterns & Design Decisions:**

*   **Monorepo Structure**: Facilitates shared code, consistent tooling, and simplified dependency management across services.
*   **Distributed Architecture**: Employs a PostgreSQL job queue for asynchronous task processing by a dedicated worker process, enabling scalable and fault-tolerant case analysis and document ingestion.
*   **Deterministic Scoring Engine**: A rule-based scoring system provides transparent and auditable case qualification.
*   **File Vault**: Secure storage for case-related documents with SHA-256 hashing for integrity verification.
*   **AI Integration**: Utilizes Anthropic Claude for medical document extraction and OCR, enhancing automated data processing.
*   **Conflict Resolution & Error Fallback**: A robust system detects conflicts, provides fail-safe modes, and an error fallback mechanism with retry logic, ensuring system stability and data quality. All failures are logged to an audit trail and a review queue.
*   **Form Engine**: A comprehensive engine for TCPA and TrustedForm compliant lead generation, featuring a tort-based form builder, embeddable JS script, live validation, background checks, and a 10-step submission pipeline with a "Final Arbiter."
*   **Taxonomy Engine**: Matches NPI provider taxonomies with medical diagnoses to identify potential mismatches.
*   **Fraud Engine**: Flags potential fraud indicators, deferring to the Final Arbiter for resolution.
*   **Compliance & Auditability**: Extensive logging of all actions and conflicts to an `audit_log` table, along with compliance-specific fields in lead records.

**Key Features & Implementations:**

*   **Dashboards**: Overview of pipeline stats, CPSR, pipeline charts, and activity feeds.
*   **Lead & Case Management**: Comprehensive features for lead intake, qualification, detailed views, document association, and distributed case processing with AI analysis and audit trails.
*   **Document Management**: Centralized document view, OCR inbox, AI document analysis for structured data extraction, PDF redaction/highlighting, side-by-side document review, medical timeline builder, and AI document drafting.
*   **Paralegal Management**: Tools for managing paralegal teams, performance tracking, and leaderboards.
*   **Analytics**: KPIs, conversion funnels, trend charts, and tort breakdown analysis, including Praxis AI Predictive Analytics for scoring.
*   **Vendor Management**: Full CRUD for vendors (lead gen, law firm, marketing, referral types) with status tracking.
*   **CSV Lead Import**: Bulk lead ingestion with auto-column mapping, preview, deduplication, conflict detection, encryption of sensitive fields, and detailed error tracking.
*   **Form Engine**: DB-backed `form_configurations` table seeded from TORT_REGISTRY on boot (auto-refreshes registry-managed fields when `updated_by IS NULL`, never overwrites admin edits). Admins can edit valid diagnoses and add/remove custom fields per tort via the Form Engine UI. Custom field values flow through embed forms → `leads.custom_fields` JSONB → lead detail (CustomFieldsCard) → CSV export (JSON-serialized). Real iframe live preview at `/api/forms/preview/:tortId`. 31 torts including 2026 MDL updates: Roundup (16 dx), AFFF (13 dx incl. UC/hypothyroid/breast cancer per MDL 2873), and new Tepezza (MDL 3079).
*   **Role-Based Access Control (RBAC)**: JWT (HS256) authentication with role hierarchy (admin > attorney > paralegal > viewer) and granular route-level access control. CI gates: the `rbac-test` validation runs the full RBAC suite (`src/lib/__tests__/rbac.test.ts` + `rbac-route-matrix.test.ts`) and `rbac-route-matrix` runs `scripts/check-rbac-route-matrix.sh`, which regenerates the live route table via `dump-route-matrix.ts` and diffs it against Section 11 of `docs/audits/rbac-remediation-2026-04-26.md` — both must pass before merging any change that touches a route or `lib/rbac.ts`.
*   **Composite Project References & Type Generation**: The `lib/*` packages are TypeScript composite projects (`emitDeclarationOnly`, `outDir: dist`) referenced from `artifacts/api-server/tsconfig.json` and the root `tsconfig.json`. Their `dist/` is **gitignored**, so consumers must regenerate it whenever a lib's source changes. Convention: always run `pnpm --filter @workspace/api-server run typecheck` (NOT `pnpm exec tsc --noEmit` directly) — the `pretypecheck` hook runs `tsc -b ../../` to build the entire reference graph incrementally before type-checking. From the workspace root, `pnpm typecheck` does the equivalent via `typecheck:libs`. To rebuild a single lib in isolation, use `pnpm --filter @workspace/db run build`. Skipping these scripts (e.g. running raw `tsc` against a consumer) reads stale `.d.ts` files and produces phantom "property does not exist" errors after schema changes.
*   **Schema-vs-Database Workflow (Drizzle, push-based)**: This project uses `drizzle-kit push` (not migrations) — `pnpm --filter @workspace/db run push` reconciles the live database with `lib/db/src/schema/*.ts` in one shot, prompting only for destructive operations. The canonical **read-only drift check** is `pnpm --filter @workspace/db run drift` (also registered as the `db-drift` validation), which inspects every Drizzle table exported from `@workspace/db`, queries `information_schema.columns`, and reports any name- or nullability-level disagreement between source and live DB; exits 0 when in sync, 1 on drift, and never mutates the database. Use it before committing schema changes and as a CI gate. Note that `drizzle-kit check` is **not** a drift check — it only validates migration-journal coherence (files in `lib/db/drizzle/`) and reports "Everything's fine" even when the schema has a column the DB lacks, because there are no committed migrations in this push-based project. The `out: ./drizzle` field in `drizzle.config.ts` exists solely to make `check` exit 0 cleanly (without it, drizzle-kit v0.31.x falls through to AWS Data API driver detection and errors with `secretArn: 'postgresql'`). An empty `lib/db/drizzle/meta/_journal.json` (`{"version":"7","dialect":"postgresql","entries":[]}`) is committed as the intentional baseline; `check` rewrites it idempotently on each run so it never appears as a diff. **Do not commit anything else under `lib/db/drizzle/`** — if `drizzle-kit generate` ever produces SQL files there, that's a deliberate switch to migration-based workflow and needs its own RFC.
*   **Dialog Accessibility Convention (Radix UI)**: Every `<DialogContent>` in the CRM MUST render a `<DialogDescription>` child (preferred — visible secondary text under the title) or set `aria-describedby={undefined}` explicitly when there genuinely is no description (the documented Radix escape hatch). Without one of these, Radix logs a `Missing 'Description' or 'aria-describedby={undefined}' for {DialogContent}` warning to the browser console AND screen readers announce only the title, leaving assistive-tech users without context for what the dialog does. This applies to all `Dialog` usages from `@/components/ui/dialog` (Radix Dialog primitive); the `AlertDialog` primitive has its own convention and is out of scope here. When adding a new dialog, prefer a short human-readable description (one sentence describing what the user is doing in this dialog).
*   **Web Auth Pipeline (CRM)**: AuthProvider boots by exchanging any stored refresh token (localStorage `mtos.refresh`/`mtos.uid`) for a fresh in-memory access token, then loads the user via `/api/auth/me`. A single-flight `refreshAccessToken()` in `artifacts/mtos-crm/src/lib/api-fetch.ts` is shared by the AuthProvider's proactive timer and on-demand 401 retries (avoids the backend's refresh-rotation theft-detection branch). `setOnUnauthorized()` on `lib/api-client-react/custom-fetch.ts` plugs the same refresh manager into generated React Query hooks, so 401s anywhere in the app trigger one refresh+retry. Login + MFA (`pages/login.tsx`, `pages/login-mfa.tsx`) gate behind `<RequireAuth>`; the dev bypass in `artifacts/api-server/src/lib/rbac.ts` (NODE_ENV !== prod/staging) is intentionally preserved so /login auto-redirects in dev. Top bar (`components/layout/top-bar.tsx`) hosts user dropdown + logout; mobile sidebar uses a Sheet slide-over below `md`; route errors are caught by `RouteErrorBoundary` keyed on location so one broken page doesn't blank the shell.
*   **Security Infrastructure**: Comprehensive security layer protecting ePHI/PII data, including token revocation, refresh tokens, MFA/TOTP, password complexity, account lockout, row-level isolation, field-level encryption with key rotation and AAD, security headers, rate limiting, security event alerting, path traversal protection, information disclosure prevention, business logic hardening, Intrusion Detection System (IDS), and AI threat analysis.
*   **Auto-Document Workflow (MTOS)**: Lead qualification automatically dispatches an e-sign packet (HIPAA + Affidavit + Retainer) per per-buyer/per-tort template toggles; on signature webhook return, an automatic doctor fax for medical records is queued. Vendor-agnostic via `provider-router` and the existing `integrations` table (Dropbox Sign + DocuSign for e-sign, Telnyx for fax, SendGrid for email). Admin pages: Buyers, Document Templates (with PDF upload to App Storage), Template Assignments matrix, Workflow Settings (vendor pickers). Lead detail has an "Automation" tab showing envelope + fax timeline. Webhook routes are mounted PUBLIC (before auth middleware) and strictly verify HMAC signatures before mutating state — bad/missing signature → 200 ack, no-op. Worker handlers are idempotent (skip if envelope already exists for lead+template) and wrap every adapter call in try/catch so the envelope/fax row always reflects the real outcome.
