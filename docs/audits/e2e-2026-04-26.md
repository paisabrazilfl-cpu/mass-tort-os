## Environment & Auth Notes
- **Auth:** This dev environment uses the bypass at `artifacts/api-server/src/lib/rbac.ts:135–146`, which auto-injects `{ id: 0, email: "dev@mtos.local", role: "admin" }` for every request. Real login, MFA, refresh-token rotation, and account-lockout paths therefore cannot be exercised end-to-end here. The middleware itself, JWT verify, refresh-token endpoints, and `requireRole` guards exist in code and unit-test cleanly; full UI auth testing requires a staging environment with `NODE_ENV=production` (or `staging`). **Recommendation: tracked under existing Task #6 (Production-ready auth & UI).**
- **Stack:** Vite + React + wouter on the frontend; Express + Drizzle on the API; a separate worker process polls `job_queue`. All four workflows (`api-server`, `worker`, `mtos-crm web`, `mockup-sandbox`) were RUNNING throughout the sweep with no errors in their logs.
- **Database:** Same dev database used by the user. Test rows created during the sweep are tagged with the suffix `680129` so they are easy to identify.

## Run 4 — **Central product flow: lead approval → automated e-sign dispatch**
This is the core thesis of the product, exercised end-to-end via the real API:

1. **Setup:** `POST /api/document-templates/assignments` with `{template_id:1, buyer_id:null, tort_type:"Roundup", enabled:true}` → 200, `template_assignments.id=2` written.
2. **Trigger:** `PATCH /api/leads/21 {status:"qualified"}` → 200, lead row updated; `audit_log` records `update_lead`.
3. **Workflow engine fired** (`audit_log` shows `lead/21/approval_dispatched`).
4. **Job enqueued:** `job_queue.id=14, job_type=send_esign_packet`.
5. **Worker picked up the job** within ~2 seconds.
6. **Envelope row created:** `document_envelopes.id=1` with correct `lead_id=21`, `template_id=1`, `signer_email=brand.new.person@unique.com`.
7. **Provider resolution executed and failed gracefully** with the exact actionable message:
   > *"No esign provider chosen. Pick one from your integrations on the Workflow Settings page."*
8. **Audit log records the failure** as `document_envelope/1/provider_resolution_failed`.
9. **Job marked `failed`** with the same actionable message — **non-retryable terminal error, will not infinite-loop the queue.**

**This is exactly the intended behavior.** The chain works; the only "missing" piece is that the user has not configured an e-sign provider yet, and the system surfaces that fact clearly instead of crashing or silently dropping the workflow.

### Low / informational
1. **`/document-templates` create form requires a non-obvious "AI Prompt" field** when source=AI. Test agent satisfied it without trouble, but a non-technical user may be confused. Consider an inline help line under the field describing what to put there. *(UX polish; not breaking.)*

Calling it out so it isn't mistaken for a bug.
3. **Two ancient `ingest_file` jobs (id=9, 10, dated 2026-04-15) failed with sanitized `../../../etc` paths.** These are residue from an earlier security test that exercised path-traversal protection. The path was correctly sanitized — the failure mode is downstream constraint validation rejecting the rewritten path, not arbitrary filesystem access. **Already covered under the security audit (Task #1).**
4. **`/financial-news` initially shows zero articles before the upstream feed loads.** Page remains stable and recovers; minor LCP/empty-state polish opportunity.

## Out of scope for this sweep (and recommended next steps to close each gap)
- **Authentication / MFA / account lockout end-to-end** — requires running in production mode against a non-bypass middleware. Tracked under Task #6 (Production-ready auth & UI).
- **CSV import committing rows** — file upload from this Playwright harness requires a real file on disk that the harness cannot supply. Recommended next step: a small server-side test that posts a multipart form with a fixture CSV and asserts the resulting `import_batches` + `leads` rows. (Estimated: 1–2 hours.)
- **Successful e-sign provider send + signed-envelope webhook → fax_med_records_request branch** — requires a configured DocuSign/SignWell credential and the provider's signing-completed webhook to actually fire. The full handler chain up to the provider call is verified working; the only untested segments are the provider's HTTP response and the inbound webhook → `onEnvelopeSigned` path. Recommended next step: a webhook simulator script that posts a synthetic "envelope completed" payload to `/api/webhooks/esign/:provider` and asserts (a) envelope row marked signed, (b) fax job enqueued, (c) worker dispatches it.
- **Successful fax provider send (Documo / SRFax)** — same as above; `handleFaxMedRecordsRequest` is wired but needs a configured fax-provider credential to fire.
- **Review-Queue and Security-Center action endpoints** (accept / reject / escalate / acknowledge / resolve) — pages render, but the action POSTs are not exercised in this sweep. Recommended next step: a 5-minute curl-based check per endpoint plus a Playwright click on each action button against a seeded queue row.
- **Vault still on local disk** — flagged for hardening under Task #1 (Security audit).
